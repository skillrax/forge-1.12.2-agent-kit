# RF Network proof — accepted

Install the production `releases/rf-network/1.0.1/rf-network-proof-1.0.1-srg.jar` in Minecraft 1.12.2 / Forge 14.23.5.2859 client and server mods folders. Replace the previous RF proof JAR; keep one version installed. Java 8; no new library dependencies. This is a creative mechanism proof: blocks and the upgrade are in the Redstone tab, with no survival recipes yet.

```text
/give @p rfnetwork:generator
/give @p rfnetwork:cable 64
/give @p rfnetwork:storage
/give @p rfnetwork:sink
/give @p rfnetwork:output_upgrade
```

## Defaults and accounting

| Part | Behavior |
|---|---|
| Generator | 1,000 RF/t shared across all six output faces and external extraction. Accepts vanilla/registered furnace solid fuels except lava buckets. One fuel slot, one GUI-only upgrade slot. Solid fuel takes priority over lava when a new reserve is needed. |
| Solid fuel | One item prepays `vanilla furnace burn ticks × 1,000` base RF of fuel reserve. Example: coal = 1,600,000 base RF; stick = 100,000. Unused reserve persists when the slot is changed, upgrade is changed, power is blocked or the world reloads. |
| Liquid fuel | Lava initially, 8,000 mB tank, 1,000 base RF/mB. Right-click with a lava bucket, or fill through any fluid-capability face. Full tanks reject additional fluid; water is rejected. Lava buckets go into the tank, not the solid slot. |
| Upgrade | 2,000 RF/t with 1.5× fuel consumed per full running tick. Thus 0.75× fuel cost per RF, or 4/3 as much RF per fuel. Base cost = four integer ledger units/RF; upgraded = three; one mB supplies 4,000 units. Fractional usage is prepaid and the remainder saved. A fully upgraded 1,000 mB supplies 1,333,333 RF plus one ledger unit retained. |
| Cable | Six-way connecting arms; zero stored/max RF. Every RF delivered costs one unit of the 60,000 RF/t allowance at **each cable on its selected path**, including ingress. All sources, ingress faces, destinations and both directions share that cable's allowance; it is gross flow, not net flow. Disjoint routes can exceed 60,000 RF/t across a whole component. A shared segment cannot. Direct machine adjacency uses endpoint limits without a cable allowance. |
| Storage | 2,000,000 RF capacity; 60,000 RF/t input combined; 20,000 RF/t output combined across every face, active push and external extraction. Each compass face cycles OFF → IN → OUT. Defaults: EAST OUT, other five IN. Unsided access is closed. Multiple IN/OUT faces do not multiply budgets. |
| Sink | Default request 1,000 RF/t. Type a whole number 0–100,000 and press Apply. Shared across all faces. Consumes immediately; no buffer, inventory, recipe or processing. Shows requested RF/t and actual RF received in the last completed tick. |

Generators push first, then storage, at world-tick END. Source and face order rotate each tick; loaded routes use breadth-first traversal and available cable budgets. This is not a guarantee of equal consumer allocation. A storage connected back into the same network through both IN and OUT faces can redistribute energy to other storage; configure faces to express the intended route. A source never routes back into itself.

Simulation does not spend fuel, RF or budgets. Commit accounts actual receipt; smaller receipt restores unused RF/fuel credit at the native source. The attempted source allowance remains spent that tick, while cable allowance counts only delivered RF. Cable external receipt returns only the actually accepted count, so an external compliant sender retains the rest. No energy resides in graph metadata or a cable, and removing a cable cannot destroy buffered energy. Ordinary breaking of **generator/storage** drops inventory but discards that machine's RF, fluid and prepaid fuel/settings; no wrench pickup in this proof.

The world/position tick ledger outlives capability reacquisition, merge/split and same-tick cable replacement. It resets on the next world tick. Neighbor tiles/capabilities are reacquired from existing chunk tile maps. A short-lived loaded-chunk index rejects absent **and queued-for-unload** chunks, without calling the provider's loading accessor. No chunk loading or chunkloader dependency is provided.

## Pending-unload correction and current acceptance

On 2026-10-14 the user reported steps 1–5 passed, expected operation at 20 TPS, and successful logout/login and full world restart. A ten-chunk cable line at render distance two continued some transfer during fast movement, then stopped. That movement test did not directly observe server chunk state; render visibility and server residency differ, and revisiting can reload a route. It does not establish a generator RF buffer: the generator has saved fuel credit, with zero stored RF.

Investigation found a real pending-unload defect: `World.getTileEntity` reaches `ChunkProviderServer.getLoadedChunk`, which clears `chunk.unloadQueued` in the pinned 1.12.2 source. The old `isBlockLoaded` guard prevented loading already-absent chunks but did not prevent cancellation of an unload queued before network END. Server-side cable-shape queries had the same problem. The patch uses existing loaded chunk/tile maps, excludes queued chunks, and rechecks all path cables at commit. A ten-chunk scenario queues the middle chunk immediately before network END: old production incorrectly transfers; patched production stops immediately, preserves the flag/fuel, allows actual unloading for six ticks, and resumes with exact conservation on reload. This establishes the defect/fix, not the exact cause or duration of every delay in the user's world. Evidence: `evidence/rf-network/1.0.1/summary.json`; original user report: `evidence/rf-network/1.0.0/user-feedback.json`.

**The proof is accepted and no manual retest remains.** The user confirmed the generator was near world spawn in spawn chunks, with storage about twelve chunks away. That matches the reproduced spawn-plus-player residency explanation and resolves the remaining concern under the user's earlier authorization to conclude if the behavior was expected. There is no requirement that leaving client render distance stop RF instantly. Evidence: `evidence/rf-network/1.0.1/user-acceptance.json`. Exact installed hash and numeric user coordinates were not independently recorded. Recipient kit extraction is the next phase.

The follow-up report used single-player with no other mods: a twelve-chunk line stopped quickly after a stationary render-distance reduction, but flight could sustain transfer, and placing storage after returning immediately received RF. The user subsequently confirmed the generator was near spawn in spawn chunks, with storage about twelve chunks away. A QA-only integrated-client replay on unchanged patched production reproduces both outcomes with normal player chunk tracking, no Forge tickets and no explicit unload calls. Far from spawn, only four of thirteen route chunks remain after flight and generation stops. Near spawn, nine protected spawn chunks plus the player's loaded radius keep all thirteen resident; another 120,000 RF is generated and stored after stopping. The replay samples actual server chunks through existing collections/tile maps. Pinned `World.isSpawnChunk` uses chunk centers within ±128 blocks in X/Z of world spawn; `WorldProviderSurface.canDropChunk` protects that region. Single-player propagates render distance to the server, whose player chunk radius has a minimum of three. F3+A calls client `RenderGlobal.loadRenderers`; it is not a server unload operation. These facts explain a viable cause of the observations, and match the user-confirmed spawn relation; exact numeric user coordinates were not recorded. Evidence: `evidence/rf-network/1.0.1/flight-summary.json`.

## Concise manual checklist

1. **Controls and connecting arms:** arrange generator → cable → storage → cable → sink along WEST to EAST (F3 shows compass direction). Open all three menus. Storage should show current / 2,000,000 RF, and EAST OUT. Cable arms should join endpoints and added upward/side branches; remove a branch and its arm disappears. Enter `1000` in the sink and Apply; reopening shows 1000.
2. **Solid fuel and upgrade:** set sink to 0, put one coal into the generator and watch storage charge at about 1,000 RF/t. Install the upgrade: about 2,000 RF/t. Try a fresh generator with one stick and the upgrade; with enough receiving space, it should ultimately yield 133,333 RF, retaining the fractional fuel remainder. Use no sink during this total check. Remove/reinsert the upgrade mid-fuel: the existing reserve remains usable and the rate changes.
3. **Lava and backpressure:** use a fresh generator, no solid fuel, and right-click with a lava bucket. With no upgrade it supplies a total 1,000,000 RF. The bucket becomes empty, tank declines only while delivering. Break the receiving cable: no further fuel/RF is spent. Reconnect: delivery resumes. Try water and a full tank; neither should consume an unaccepted container. Solid plus lava should spend solid first.
4. **Face settings and shared output:** charge a storage, disconnect its generator, and attach two sinks on two OUT faces, each requesting 15000. Their combined actual drain is at most 20000 RF/t, not 30000; allocation can vary. Set a face OFF or IN and its outgoing drain stops. With a single sink requesting 100000, storage still supplies at most 20000. Change request to 0: drain stops. Invalid text/ranges should be rejected.
5. **Branches, loop and split:** join multiple fueled generators or charged storage blocks to a branching cable network with two sinks. Add a cable loop: no multiplied RF. Break/rejoin the shared segment or replace a cable: source fuel and storage RF remain; sinks disconnected from all sources stop, then resume. To observe the 60000 cable limit, use four charged storage sources (each OUT toward one shared cable), then branch that cable to two sinks requesting 50000 each. Total is at most 60000; all four storage outputs total at most 80000 without the shared bottleneck.
6. **Persistence and chunk boundary:** choose recognizable storage faces and sink request; leave a partially used generator with lava, solid fuel and upgrade. Save, fully close and reopen. RF, inventory, lava, prepaid fuel and settings should persist. Across a chunk boundary, allow the consumer side or source side to unload without chunkloaders: no phantom delivery/fuel spending; returning reconnects the loaded network. Ordinary gameplay loading can keep nearby chunks loaded, so automation provides the controlled unload evidence.

The checklist remains a reference; no replay is pending. Reopen only for a concrete regression, identifying the actual modpack and third-party block/version if relevant. Kit extraction can now proceed.

## API and compatibility boundary

The actual API is pinned Forge `net.minecraftforge.energy.IEnergyStorage` through `CapabilityEnergy.ENERGY`, using the opposite neighbor face. RF is the display unit. Native proof blocks and a QA-only partial-acceptance FE handler are tested; **no Ender IO, Thermal, CoFH or other third-party integration has been runtime-tested**. Generators/storage actively push; external FE sources may push into cables. Cables do not expose extraction, so pull-only consumers must extract from an OUT storage face instead. The generator exposes generated-on-demand extraction with zero stored RF; receivers should accept its active push.

Legacy CoFH RF uses distinct sided interfaces, such as `cofh.redstoneflux.api.IEnergyReceiver.receiveEnergy(EnumFacing, int, boolean)`; implementing FE does not implement that interface. Primary sources: [CoFH 1.12 RF interface](https://github.com/CoFH/RedstoneFlux-1.12-Legacy/blob/1.12/src/main/java/cofh/redstoneflux/api/IEnergyReceiver.java), [CoFH API overview](https://github.com/CoFH/RedstoneFlux-1.12-Legacy). Forge API and packet signatures were checked in the kit's pinned mapped source: `IEnergyStorage`, `CPacketEnchantItem.writePacketData`. No API classes from third parties are repackaged. Malformed handlers returning negative or excessive committed counts are rejected; arbitrary reentrant/noncompliant handlers, performance parity, large networks and broad modpack reliability are unproven.

## Maintainer checks and reusable lessons

Authoritative production files: `src/main`; isolated QA: `src/evaluation` plus `build-overlay.gradle`. Use a new kit checkout, copy both source sets and overlay, set Gradle group `dev.agentic.rfnetwork`, archives name `rf-network-proof`, and apply the overlay. Keep pinned build configuration and synchronized mod version. Run `agent.ps1 -Action check -Profile mod`, then `qa/integration/Invoke-RfNetworkServer.ps1 -Workspace <checkout>` and `Invoke-RfNetworkClient.ps1`. For the pending-unload reproduction, additionally apply `build-chunk-overlay.gradle`: it selects only `QueuedChunkChecks`, without replaying the full accounting checks. Export through checkout `tools/Export-Release.ps1` only with a fresh mod PASS. Original evidence: `evidence/rf-network/1.0.0/summary.json`; focused patch: `evidence/rf-network/1.0.1/summary.json`.

For the reported flight/residency question, use an isolated checkout and additionally apply `build-flight-overlay.gradle`, selecting `FlightChecks` instead of the menu check. It creates a new QA world and replays server player positions through ordinary player chunk-map updates, first far from spawn and then near spawn. This is a bounded two-scenario integrated-server replay, not manual flying, a performance benchmark or proof of the user's coordinates. Observers must reacquire restored tile objects after unload/reload, and rate accounting must use server ticks rather than assuming client and server scheduling stay identical.

The bounded checks use real server-world production methods for exact accounting, plus normal ticks with two actual partial unload/save/reload intervals and storage/generator/sink saved state. They include full capacity, fractional fuel exhaustion, multiple sources/consumers, branch bottleneck, loop simulation, same-tick cable replacement and a partial committed receiver. Client checks use real menus, split signed-short property transport, the numeric text field/Apply packet, invalid range rejection and screenshots. These are automated observations; manual acceptance and a separate-JVM user save/reopen remain distinct.

Reusable mechanisms established by these observations: budgets belong to the world position/tick, not a face wrapper or graph component; route simulation needs virtual endpoint and path reservations to avoid double counting; fuel credit uses integer units and is consumed only for delivered demand; partial receipts refund native source state; transient sink display snapshots completed ticks; large properties need split fields; rich controls need a validated packet because vanilla enchant actions are bytes. `World.setTotalWorldTime` is client-only in the pinned server runtime: QA advances `WorldInfo.setWorldTotalTime` for synchronous budget checks. **Loaded access can cancel unloading:** use the provider's existing chunk collection and existing tile maps, reject `unloadQueued`, and test queueing after provider ticking but before mod routing. Even QA `getLoadedChunk` observations can clear that flag; use side-effect-free collection observations during an unload test. Spawn residency plus player-loaded chunks can preserve a whole route; F3+A is not server unload evidence. Routing rebuilds loaded topology per offer for simplicity; profile an actual workload before adopting this traversal for large modpacks. Extract these mechanisms once into recipient guidance; keep QA separate.
