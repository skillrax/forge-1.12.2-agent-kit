# Block Actions concept proof

A bounded Minecraft 1.12.2 / Forge 14.23.5.2859 interactive console. Production is `src/main`; assertions and graphical preview automation are in `src/evaluation`, excluded from the exported JAR. There is no ticking, RF cost, tier system or automation. User passed all seven representative gameplay steps, including all three fluids and actual world restart. Acceptance: evidence/block-actions/1.0.0/user-acceptance.json.

## Use and representative manual checklist

Install `releases/block-actions/1.0.0/block-actions-proof-1.0.0-srg.jar` in a Forge 1.12.2 test instance. Use a creative test world with commands enabled. Get the console with `/give @p blockactions:machine`, or find **Block Actions Console** on the Redstone tab. Right-click to open it. A diamond pickaxe belongs in **Tool**; blocks/buckets in **Item**; the six right-hand slots are outputs. Shift-click routes vanilla tools to Tool and other items to Item. Outputs cannot accept manual insertion.

The machine starts paused and acts only on **STEP once** while armed. Leaving it armed does not schedule actions. Target cycles through all six immediate neighbors; its XYZ is shown in the menu. Looking at the console shows the target's cyan box. All controls cycle forward. Mining policy affects mining only. Yaw, hit face and hit Y affect player placement. Direct meta affects direct placement only; hit X/Z are fixed at 0.5. Clear outputs and the target between unrelated checks. Use an open area at normal height; keep the surrounding chunks loaded.

1. **Pause and mining.** Put stone at the displayed target and a diamond pickaxe in Tool. STEP while paused leaves it intact. Arm, choose Mine / Ordinary, then STEP: one cobblestone, one durability point, no XP. Replace the stone, choose Silk touch: one stone. Try diamond ore with a wooden pickaxe: Tool cannot harvest, ore stays. A diamond pickaxe in Ordinary produces one diamond plus 3–7 saved XP; Silk produces the ore and zero XP. Fortune III is optional: diamond count is 1–4 per ore, not a fixed bonus.
2. **Backpressure and contents.** Fill all six outputs with full stacks of sticks, then try mining stone: Output full, target/tool/XP unchanged. Empty a slot and retry. Any chest (empty or containing items), or a dispenser, is rejected intact as a tile entity; bedrock is rejected as unbreakable. Ordinary glass legitimately produces no drops, while Silk glass produces a glass item.
3. **Player placement state.** Choose Place / Player item-use, empty the target and supply oak stairs. Set Yaw East, Hit face East, Hit Y 0.75: one stair faces east with its upper half selected. For a stone slab, East + 0.75 produces a top slab; Up + 0.25 produces a bottom slab. Occupied targets are rejected; this proof does not merge existing slabs. A matching slab next to the target on the hit face is also rejected to prevent vanilla ItemSlab from merging outside the visible target.
4. **Direct state and leaves.** Place oak leaves using Player item-use: ItemLeaves supplies metadata bit 4, making DECAYABLE=false. Remove them, choose Direct state / meta 0 and place oak leaves again: DECAYABLE=true (natural leaves, liable to decay). For stairs, direct meta 4 gives vanilla's top/east state regardless of yaw/hit. Direct meta is intentionally raw: it can select another subtype of the supplied block family. This is a semantic test console, not a balanced survival placer. F3 targeted-state properties can confirm the result.
5. **Sources and buckets.** Choose Load bucket with a single water bucket in Item: input consumed, one empty output bucket, tank +1000 mB. Pour source into an air target: tank -1000, one water source. Collect source: target becomes air, tank +1000. Unload bucket with an empty bucket in Item: tank -1000, one filled output bucket. Repeat the same short cycle with lava or Proof Fluid (its green Forge universal bucket appears under Miscellaneous; `/give @p forge:bucketfilled 1 0 {FluidName:"blockactions_proof",Amount:1000}` also supplies one). Tank mixing/full tank, blocked bucket outputs and flowing fluid are rejected without consumption. Source collection can be followed by normal vanilla source regeneration; nearby water may therefore refill the hole.
6. **Dimension restriction.** In the Nether, load water and try Pour source: Water rejected in Nether, 1000 mB retained, no block created. Lava is allowed. Bucket actions are explicit tank transfers; they do not use bucket ray tracing or the FillBucketEvent pathway.
7. **Save/reopen once.** Leave a block stack, tool, some tank fluid and saved XP; select nondefault controls. Save/exit the world and reopen. Contents, XP and settings persist; the machine restarts paused. Ordinary breaking drops its eight inventory slots and discards its tank/XP/settings. There is no packed-state pickup in this proof.

Report a failed step with the status, target XYZ, selected context/policy/face/yaw and item/tank counts. No third-party protection or special-item acceptance is inferred from these vanilla checks.

## Explicit semantics and limits

Mining retains the actual vanilla tool material and harvest eligibility (`canHarvestBlock`). Tool must be a vanilla ItemTool/shears, or empty hand for blocks that permit it. Policy replaces Silk/Fortune on a temporary copy; Ordinary removes both, Silk applies level 1, Fortune is bounded at I–III. Other enchantments stay; the stored tool's enchantments are unchanged and its actual durability/Unbreaking behavior is used after successful removal. Unsupported silk harvest falls back to vanilla ordinary drops. Zero-drop results are valid. `doTileDrops=false` suppresses captured item drops and stored XP.

`ForgeHooks.onBlockBreakEvent` supplies cancellable BreakEvent and XP. `Block.harvestBlock` supplies the ordinary/silk harvest callbacks and HarvestDropsEvent, captured once through Forge's protected thread-local Block drop capture. We intentionally harvest into that capture **before** removal so the exact result can be reserved. Full output discards the planned drops; no world block, real tool, XP or inventory is spent. A failed attempt may advance vanilla random draws / run harvesting event listeners. After reservation, `removedByPlayer`/`onBlockHarvested`, `onPlayerDestroy` and the real tool's `onBlockDestroyed` run. Tool destruction emits Forge's destroy-item event. This order differs from PlayerInteractionManager's removal-then-harvest and is restricted to the explicit vanilla block set. It does not claim atomicity against listeners that mutate the world or spawn entities independently of Block.spawnAsEntity. No arbitrary mod blocks/tools are supported.

XP is a saved numerical ledger capped at 1,073,741,823, not spawned or granted to a nearby player. There is no XP redemption control. Tile entities are rejected before harvesting (including inventory contents); no double chest search, extraction, tile NBT copy, or loot-table opening occurs. Supported families are stone/cobble/dirt/grass/sand/gravel, planks/logs, glass/obsidian, the vanilla ore set, leaves, stone/wood slabs and oak/cobble/brick stairs. TNT, plants/crops, doors/beds, containers, falling-block items outside that set and arbitrary special/modded items are unsupported. Normal sand/gravel gravity and leaf decay still apply after an action.

Player placement invokes `RightClickBlock` (cancellation/use-item denial honored), then `ItemStack.onItemUse`, which enters pinned `ForgeHooks.onPlaceItemIntoWorld`: ItemBlock/ItemSlab/ItemLeaves callbacks, placement state computation, onBlockPlacedBy, and Forge PlaceEvent snapshots/rollback. It targets the replaceable cell itself; it does not activate a neighboring block, call onItemUseFirst, or simulate the entire network right-click manager. Metadata comes from the supplied item; ordinary tags remain on its copied stack, but BlockEntityTag and BlockStateTag are explicitly rejected. Supported vanilla targets must be replaceable, nonliquid and have no tile entity; ItemBlock's mayPlace/collision rules still apply.

Direct placement uses the supported ItemBlock's `getStateFromMeta(selected 0..15)` rather than item metadata, getStateForPlacement, onBlockPlacedBy or NBT transplantation. It still enforces mayPlace, emits a cancellable PlaceEvent against a captured replacement, restores the snapshot on cancellation, then runs onBlockAdded and neighbor/client notifications on success. There is no universal placed-by-player flag. Leaf persistence here comes from ItemLeaves metadata; stair/slab state comes from placement callbacks or raw metadata. Natural direct leaves can decay. Arbitrary tile-entity NBT transplantation is not offered.

Each step creates a short-lived survival FakePlayer subclass with a stable UUID derived from dimension + machine position, named `[BlockActions]`. It is not the menu opener or a real player's identity; ownership/permissions are not inherited. Position is target center X/Z and target Y−1, yaw is selected, pitch zero, sneaking false, main hand is the action's copied item/tool and inventory otherwise empty. Its position-vector override avoids pinned FakePlayer's hardcoded origin. A packet-discarding connection is required because pinned ForgeHooks sends correction packets to the actor. World/provider `isBlockModifiable` (including vanilla spawn protection) and canPlayerEdit guard world actions. Cancellable BreakEvent, RightClickBlock and PlaceEvent paths were tested locally; named modpack protection plugins were not. Direct fluid actions use Break/Place events, not vanilla bucket-use/FillBucketEvent semantics.

Water/lava source level 0 and this proof's BlockFluidClassic source are exactly 1000 mB. Flowing/falling levels are rejected. Collect uses air replacement; pour requires air, creates a level-0 source and schedules normal fluid updates. Water in vaporizing dimensions is rejected without spending fluid; no evaporation/sound-only consumption. One 4000 mB tank accepts only one fluid at a time. Bucket transfers accept only vanilla water/lava buckets or Forge's universal bucket containing a supported 1000 mB fluid; arbitrary cells/containers are rejected. No fluid/item capability automation is provided.

All actions execute on the logical server. A conservative 32-block X/Z halo around machine and target must consist of existing, nonqueued chunks; Y must be 1–254 and target inside the world border. LoadedAccess scans ChunkProviderServer.getLoadedChunks and never uses getLoadedChunk, which clears unloadQueued in the pinned version. Reject before any world callbacks; save-only dirty marking uses the existing owner Chunk. Menu validity/routing likewise read existing tile maps. The halo covers the supported vanilla light/neighbor/leaf paths, not arbitrary third-party callbacks. Normal later vanilla fluid/falling/decay ticks are not machine-driven operations and retain their normal engine behavior. No cached neighbor tiles or automatic requeue/resume loop exists.

## Evidence and reproduction

Evidence index: `evidence/block-actions/1.0.0/summary.json`; preserved artifact/checklist: `releases/block-actions/1.0.0/`. The final dedicated world run made 50 focused assertions; a separate JVM checked persisted state and default pause. Graphical checks invoke actual menu mouse callbacks and normal server packets, exercise mining, placement and bucket loading, then capture the tank and in-world target. Screenshots are visually inspected. Developer-classpath gameplay evidence is distinct from installing the SRG JAR in an independent launcher; user acceptance is recorded in the separate acceptance file.

To reproduce in a **new** source checkout: run `kit/tools/New-Checkout.ps1 -Destination <new .work path>`, copy fixture `src/main` and `src/evaluation` into its `src/`, copy build-overlay.gradle as block-overlay.gradle, and append `apply from: 'block-overlay.gradle'` to build.gradle. Keep the pinned kit dependencies. Run agent.ps1 check/mod, then `qa/integration/Invoke-BlockServer.ps1 -Workspace <path>` twice (second invocation verifies persisted state), and `qa/integration/Invoke-BlockClient.ps1 -Workspace <path>`. The overlay uses a disposable `block-actions-delivery` server world; a previously successful world enters reload verification rather than rerunning the first scenario. Use a new checkout/world when changing server assertions. Run tools/Export-Release.ps1 after a fresh mod PASS. Production JARs must not contain dev/agentic/blockchecks.

Reusable lessons: inspect the exact ItemStack wrapper, not just ItemBlock.onItemUse, for Forge rollback; ItemSlab can mutate the adjacent cell; ItemLeaves supplies persistence through metadata; base FakePlayer has both a null connection and an origin position vector; harvesting before reservation requires an explicit supported-block scope and callback-order caveat. Direct placement should expose that it skips placement callbacks, while still honoring explicit cancellation and accounting.

Accepted production lessons: use the supplied tool enchantments by default rather than the fixture selector; treat strict vanilla harvest/registry restrictions and Nether reject-and-retain as explicit proof policies, not universal requirements.
