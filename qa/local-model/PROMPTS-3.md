# Local-model trial prompts, series 3 (S0-S7)

Held out: written without reading the kit's docs, tools or earlier prompts and results. Do not show this file to an agent or tune the kit to these prompts.
Paste only the **Prompt:** text, verbatim, into a fresh trial folder. **Grade:** lines are for the human grader only.

## S0 - Where am I command

**Prompt:** I keep getting lost on my server and pressing F3 shows way too much stuff. Can you make a mod that adds a chat command, /whereami, that anyone can use (not just ops)? It should tell me in chat my coordinates rounded to whole blocks, which dimension I'm in (Overworld, Nether, End), what biome I'm standing in, and how bright it is where I'm standing. If I type /whereami share it should send the same info to everyone on the server with my name in front, so my friends can find me. If someone types it wrong it should tell them how to use it, and if it's run from the server console it should just say it only works for players instead of breaking.

**Grade:** Needs a `CommandBase` subclass registered in `FMLServerStartingEvent` via `event.registerServerCommand`; `getRequiredPermissionLevel()` returns 0 (default is 4, so non-ops get "no permission" - check by opening to LAN without cheats or using a second account); `checkPermission` must not be left requiring op. Coordinates from `MathHelper.floor` of posX/Y/Z or `player.getPosition()`. Dimension from `player.dimension` / `world.provider.getDimensionType().getName()`, mapped to friendly names, unknown dimensions still print something. Biome: `world.getBiome(pos)`; note `Biome.getBiomeName()` is `@SideOnly(CLIENT)` in 1.12.2 - works in runClient's integrated server but would crash a dedicated server; full marks use the registry name or a translation key/`TextComponentTranslation`, using `getBiomeName` is a "partly" with a note. Brightness: `world.getLightFromNeighbors(pos)` or `getLight(pos)` (0-15); bonus for splitting block/sky light. `share` broadcasts via `server.getPlayerList().sendMessage(...)` with the player's name. Wrong args -> `WrongUsageException` with a usage string from `getUsage` (lang key or literal). Non-player sender: `getCommandSenderAsPlayer` throws `PlayerNotFoundException`, which shows a clean red message - acceptable; a manual `instanceof EntityPlayerMP` check is fine too. Bonus: `getTabCompletions` offers `share`. In runClient: run in Overworld, Nether (through a portal; 1.12 `/tp` cannot change dimension), stand by a torch vs in darkness, type `/whereami foo`, run from a command block (should print an error, not crash). Partly: works but needs op, or prints raw dimension IDs, or `share` only messages the sender.

## S1 - Glowberry crop

**Prompt:** I want a new farm crop called Glowberries. You get Glowberry Seeds sometimes when breaking tall grass, just like wheat seeds. You plant them on farmland, they grow through 4 stages that look different, and bonemeal speeds them up. They should only grow when there's enough light, like normal crops. When fully grown the bush gives off a little light, like a dim torch, and breaking it drops 1-3 Glowberries and 1-2 seeds; breaking it early just gives back the seed. Glowberries can be eaten (a small snack, about like a sweet berry) and eating one gives a few seconds of night vision. Villagers or animals don't need to care about them. Please make sure they break if the farmland under them gets trampled, the same as wheat.

**Grade:** Block extends `BlockCrops` with overridden `getSeed()`/`getCrop()`. Four stages means either a custom `PropertyInteger` AGE 0-3 with overridden `getAgeProperty()`, `getMaxAge()` and `createBlockState()` (gotcha: `BlockCrops`' constructor calls `getAgeProperty()` before subclass instance fields exist, so the property must be a static field), or keeping 0-7 and mapping to 4 models in the blockstate JSON - both acceptable if all states have models (no purple/black missing-model in any stage). Seeds: `ItemSeeds(crop, Blocks.FARMLAND)` (or `IPlantable` item) registered; grass drop via `MinecraftForge.addGrassSeed(new ItemStack(seeds), weight)`. Growth through inherited `updateTick` (light >= 9 at pos.up, random tick); bonemeal works through inherited `IGrowable` (`grow` respects the custom max age - check it never sets age beyond max). Light at final stage: override `getLightValue(IBlockState, IBlockAccess, BlockPos)` returning e.g. 7 only when mature; `world.checkLight` happens automatically on state change. Drops: override `getDrops(NonNullList, IBlockAccess, BlockPos, IBlockState, int fortune)` - mature 1-3 berries + 1-2 seeds, immature 1 seed; `getItemDropped` alone gives wrong counts. Food: `ItemFood(2, 0.1F, false)` with `setPotionEffect(new PotionEffect(MobEffects.NIGHT_VISION, ~100-200, 0), 1.0F)` or `onFoodEaten` override (server-side only). Trampling and lack of farmland come free from `BlockBush`/`canSustainPlant` - check that placing seeds on dirt fails and jumping on farmland breaks the crop and drops a seed. Lang entries for all items/blocks. In runClient: break grass until seeds drop (or creative tab), plant, bonemeal through each stage, check F3 light level next to a mature bush in darkness, cover the crop so light < 9 and confirm no growth (`/gamerule randomTickSpeed 100` helps), eat a berry and see night vision. Partly: crop works but uses 8 visual stages with missing models, or drops are wrong at immature stage, or no grass seed drop.

## S2 - Pulse counter block

**Prompt:** I build a lot of redstone contraptions and I want a Pulse Counter block. It faces a direction when placed, like a repeater, with an input on the back and an output on the front. Every time the input turns on (not while it stays on, just each time it switches on) the counter goes up by one, and the redstone signal coming out of the front gets stronger by one, up to 15. On the 16th pulse it wraps back to 0. Right-clicking it with an empty hand should tell me the current count in chat, and sneak-right-clicking resets it to 0. A comparator reading from it should also show the count. The count must stay the same when I leave and reload the world. It should be craftable from a repeater, a comparator and some stone.

**Grade:** Block with `BlockHorizontal.FACING` (placement facing via `getStateForPlacement` with `placer.getHorizontalFacing().getOpposite()` or equivalent), plus a TileEntity holding the count (4 facings x 16 counts cannot fit in 4 bits of metadata, so a count blockstate property only works if facing moves into the TE; check whatever approach is used survives a reload). Edge detection: in `neighborChanged`, read `world.getRedstonePower(pos.offset(back), back)` (or `getRedstonePower(pos.offset(facing.getOpposite()), facing.getOpposite())`) and compare to a stored "was powered" flag; counting while held high or double-counting on one pulse is a fail. Output: `canProvidePower` true, `getWeakPower(state, world, pos, side)` returns count only toward the output neighbour. Gotcha: `side` is the direction from the querying neighbour into this block (vanilla diodes return power when `side == FACING` while outputting at `pos.offset(FACING.getOpposite())`), so for an output at `pos.offset(out)` the check is `side == out.getOpposite()`; test with dust on all four sides - only the front should light. Must not power the input side (would self-trigger). After changing count call `world.notifyNeighborsOfStateChange(pos, this, false)` and/or `notifyNeighborsOfStateChange(pos.offset(facing), this, false)` so the dust updates. Comparator: `hasComparatorInputOverride` + `getComparatorInputOverride`, and `world.updateComparatorOutputLevel` when count changes. Persistence: TE `writeToNBT`/`readFromNBT` + `markDirty()`; TE registered with `GameRegistry.registerTileEntity(Class, ResourceLocation)`. Gotcha: Forge's default `TileEntity.shouldRefresh` for modded TEs returns true on any state change, so if a blockstate property (e.g. POWERED) changes, the TE and its count are wiped unless `shouldRefresh` is overridden to compare blocks. Interaction: `onBlockActivated` only acts on server (`!world.isRemote`), empty main hand, sneak = reset; return true on both sides so the arm swings. Recipe JSON in `assets/<modid>/recipes`. In runClient: lever on the back, toggle 3 times -> output 3, dust strength readout via F3/dust length; hold lever on for a while (count must not increase); button pulses; 16 pulses -> 0; comparator from the side; sneak reset; save/quit/reload keeps count; rotate placement 4 ways. Partly: counts correctly but outputs on every side, or loses count on reload/state change, or no comparator support.

## S3 - Gathering and Soulbound enchantments

**Prompt:** Add two new enchantments. "Gathering" goes on pickaxes, axes, shovels and swords: anything the item breaks or kills drops straight into my inventory instead of on the ground, and if my inventory is full the leftovers drop normally. "Soulbound" can go on any tool, weapon or armor piece: when I die, soulbound items stay with me and are back in my inventory when I respawn, while everything else drops like normal. Both should be possible to get from the enchanting table and as enchanted books, and combine on an anvil. Soulbound should be rare. I'd also like a settings screen in the Mods menu where I can turn each enchantment off, and set whether Gathering also picks up experience orbs straight away.

**Grade:** Two `Enchantment` subclasses (constructor `(Rarity, EnumEnchantmentType, EntityEquipmentSlot[])`; Gathering type `DIGGER` plus `canApplyAtEnchantingTable`/`canApply` override to include swords, or `EnumEnchantmentType.ALL` filtered; Soulbound `BREAKABLE`/`ALL` with `Rarity.VERY_RARE`), registered in `RegistryEvent.Register<Enchantment>` with registry name and `setName`, lang `enchantment.<modid>.<name>`; min/max enchantability sensible so the table can roll them; books come free from registration (check creative Enchanted Books tab lists them). Gathering: `BlockEvent.HarvestDropsEvent` - when `getHarvester()` is a non-fake player holding a Gathering item, move each stack into the inventory with `addItemStackToInventory` and remove/shrink in `getDrops()` (leave leftovers); mob kills via `LivingDropsEvent` with `source.getTrueSource()` player, moving `EntityItem` stacks and cancelling/removing entries. XP option: `BlockEvent.BreakEvent.setExpToDrop(0)` + `player.addExperience`, and `LivingExperienceDropEvent` for mobs. Soulbound: `PlayerDropsEvent` (fires for players, not plain `LivingDropsEvent` only) - remove soulbound `EntityItem`s and keep them somewhere (e.g. a static map keyed by UUID, or player NBT `getEntityData()`/persisted tag), then restore in `PlayerEvent.Clone` when `isWasDeath()` (by then `dropAllItems` has emptied the old inventory, so the stash is required; restoring in `PlayerRespawnEvent` also works). Full marks if items survive and never duplicate; check with `keepInventory` true (no duplication) and that armor goes back in armor slots or at least inventory. Config: `@Config(modid=...)` class with booleans, plus `@Mod.EventBusSubscriber` handler for `ConfigChangedEvent.OnConfigChangedEvent` calling `ConfigManager.sync(modid, Config.Type.INSTANCE)`; Forge 1.12.2 auto-generates the Mods-menu config GUI for `@Config` (no guiFactory needed). Disabled enchantment should stop working (and ideally not appear at the table via `canApplyAtEnchantingTable`). All logic server-side. In runClient: `/enchant @p <modid>:gathering 1`, mine stone and kill a cow with full and empty inventory, die with mixed soulbound/normal items in lava and in a pit, try both on an anvil with books, toggle settings in Mods > Config and re-test. Partly: enchantments register and appear but one effect fails, or Soulbound duplicates items with keepInventory, or config file exists but no GUI/sync.

## S4 - Maple syrup fluid and tank

**Prompt:** I want a new liquid, Maple Syrup, that comes in a bucket and can be poured out in the world. It flows like water but slower and shorter, and any mob or player standing in it gets slowed down. It should be gotten by crafting a bucket with sugar and wood logs, just for testing. I also want a Tank block that holds up to 16 buckets of any liquid (water, lava, syrup). Right-clicking the tank with a full bucket pours it in, with an empty bucket takes a bucket out, and with an empty hand tells me in chat what's inside and how much. If I break the tank it should keep its liquid inside when I place it back down. Hoppers don't matter, but pipes from other mods should be able to connect, and a comparator next to the tank should show how full it is.

**Grade:** Fluid: `FluidRegistry.enableUniversalBucket()` called in a static initializer of the @Mod class (must be before preInit, or the bucket silently won't exist); `new Fluid("maple_syrup", stillRL, flowingRL)` with higher viscosity/density, `FluidRegistry.registerFluid` then `FluidRegistry.addBucketForFluid`; `BlockFluidClassic(fluid, Material.WATER)` registered with item-less registration, `setQuantaPerBlock(4)` or so for shorter flow, `fluid.setBlock`. Slowdown: `onEntityCollidedWithBlock` applying `MobEffects.SLOWNESS` or motion damping, server-side. Rendering: custom `StateMapperBase` / `ModelLoader.setCustomStateMapper` pointing at a `forge:fluid` blockstate - invisible/missing-texture fluid is a visual-only "partly". Recipe output for a universal bucket needs NBT (`{FluidName:"maple_syrup",Amount:1000}` via `FluidUtil.getFilledBucket`) - a JSON recipe can't easily do this, so a code-registered `IRecipe`/`ShapelessOreRecipe` with `FluidUtil.getFilledBucket(new FluidStack(fluid,1000))` is the clean path. Tank: TE with `FluidTank(16000)`, exposes `CapabilityFluidHandler.FLUID_HANDLER_CAPABILITY` in `hasCapability`/`getCapability` (that is what lets mod pipes connect), NBT via `tank.writeToNBT`/`readFromNBT`, `markDirty` on change (override `onContentsChanged`). Right-click: `FluidUtil.interactWithFluidHandler(player, hand, world, pos, facing)` handles all buckets incl. vanilla water/lava and universal; empty hand prints `getFluid().getLocalizedName()` + amount mB server-side. Keep contents: write tank NBT to the dropped ItemStack (`getDrops` needs the TE, so use the `removedByPlayer` delay / `harvestBlock` override pattern, or `BlockEntityTag` in stack NBT) and read back in `onBlockPlacedBy`. Comparator: `getComparatorInputOverride` scaled 0-15, `updateComparatorOutputLevel` on change. Bonus: `getUpdatePacket`/`getUpdateTag` sync if a TESR shows the level. In runClient: craft syrup bucket, pour, walk through (slowed), pick back up with empty bucket; fill tank with 16 water buckets, 17th refused (bucket kept); mix lava into water tank is refused; break, replace, check contents; comparator strength. Partly: tank works with vanilla buckets but syrup bucket missing, or tank empties when broken, or no fluid capability.

## S5 - Fetching wolves

**Prompt:** I love my tamed wolves and want them to be more useful. If I right-click one of my own tamed wolves while holding a stick, it switches between normal mode and Fetch mode, and tells me in chat which mode it's in now (it shouldn't sit down or stand up when I do this). In Fetch mode, the wolf looks for dropped items on the ground within about 12 blocks of me, runs over, picks one up, carries it back and drops it at my feet, then goes for the next one. It can only carry one stack at a time. It shouldn't fetch while it's sitting, and other people's wolves shouldn't listen to me. If the world is saved while a wolf is carrying something, it should still have it after reloading, and if the wolf dies it drops what it was carrying. Wild wolves and other animals stay completely normal.

**Grade:** Per-wolf data needs a capability attached to a vanilla entity: interface + impl + `Capability.IStorage`, `CapabilityManager.INSTANCE.register` in preInit, `@CapabilityInject` field, `AttachCapabilitiesEvent<Entity>` adding an `ICapabilitySerializable<NBTTagCompound>` only when `event.getObject() instanceof EntityWolf` (mode + carried ItemStack). Alternatively `entity.getEntityData()` NBT is acceptable but less clean. AI: on `EntityJoinWorldEvent` (server side only, `!world.isRemote`) add a custom `EntityAIBase` to `wolf.tasks` at a priority above follow-owner but below sit (`EntityAISit` is priority 2; fetch around 3-5), with `setMutexBits` covering movement (1) so it doesn't fight `EntityAIFollowOwner`; `shouldExecute` checks tamed, mode on, `!isSitting()`, owner present, an `EntityItem` within 12 blocks of owner (`world.getEntitiesWithinAABB(EntityItem.class, ...)`, skip `isDead`/`cannotPickup`); uses `getNavigator().tryMoveToEntityLiving`/`tryMoveToXYZ`; on reach, copies stack into capability and `setDead()`s the item; returns to owner and spawns an `EntityItem` at owner's feet (or gives to inventory). Interaction: `PlayerInteractEvent.EntityInteract` (fires for both hands - handle `EnumHand.MAIN_HAND` only), check `wolf.isTamed() && wolf.isOwner(player)` and stick held, toggle, message, then `event.setCanceled(true)` and `setCancellationResult(EnumActionResult.SUCCESS)` so `EntityWolf.processInteract` doesn't toggle sitting - test that the wolf's sit state doesn't change. Non-owner: nothing happens (falls through to vanilla). Death drop: `LivingDropsEvent` adding the carried stack, or `entityDropItem` in `LivingDeathEvent`. Persistence works through the serializable capability; verify by reload mid-carry. Bonus: carried item shown client-side (needs a sync packet + render layer) - not required. In runClient: tame two wolves, toggle with stick, scatter items with Q, watch fetch; sit one; drop item 20 blocks away (ignored); save & quit while carrying; kill a carrying wolf with `/kill @e[type=wolf,c=1]`; second player/LAN or untamed wolf right-click does nothing special. Partly: fetching works but mode doesn't persist, or toggling also sits the wolf, or wolf never gives the item back.

## S6 - Tool belt with hotkey

**Prompt:** I'm always running out of hotbar space. Give every player an invisible tool belt with 3 extra slots. When I press a key (R by default, changeable in the Controls menu under the mod's own section), the item in my hand swaps around with the belt: hand goes to belt slot 1, slot 1 to slot 2, slot 2 to slot 3, and slot 3 into my hand, so pressing it repeatedly cycles through all four. Empty slots count too, so I can put things in by cycling. A small row of three item icons near the hotbar should show what's in the belt right now. The belt has to work on servers, so it can't be possible to cheat by editing the client. The belt items must still be there after logging out, after going through a Nether portal, and after respawning if keepInventory is on; without keepInventory they drop on death with the rest of my stuff.

**Grade:** Player capability (interface, `IStorage`, impl with `ItemStackHandler(3)` or `NonNullList<ItemStack>`), registered in preInit, attached in `AttachCapabilitiesEvent<Entity>` for `EntityPlayer` with `ICapabilitySerializable`. Keybind: `new KeyBinding("key.<modid>.cycle", Keyboard.KEY_R, "key.categories.<modid>")` registered with `ClientRegistry.registerKeyBinding` in client-only code (client proxy or `@SideOnly`/`@EventBusSubscriber(value=Side.CLIENT)`), polled with `isPressed()` in `InputEvent.KeyInputEvent` or `ClientTickEvent`; no client classes (`Minecraft`, `KeyBinding`, `GuiScreen`) referenced from common code - check it would load on a dedicated server (bonus if `runServer` starts). Networking: `SimpleNetworkWrapper` via `NetworkRegistry.INSTANCE.newSimpleChannel`, a C->S `IMessage` that carries no item data (just "cycle"), registered with `Side.SERVER`; handler gets `ctx.getServerHandler().player` and runs the swap inside `player.getServerWorld().addScheduledTask(...)` (doing it on the netty thread is a bug); server ignores dead/spectator players. Server performs the rotation on `player.inventory.getCurrentItem()`/`setInventorySlotContents(currentItem, ...)` and the capability, then sends an S->C sync message (`Side.CLIENT`, handler uses `Minecraft.getMinecraft().addScheduledTask`) with the 3 stacks (`ByteBufUtils.writeItemStack`). Also sync on `PlayerLoggedInEvent`, `PlayerRespawnEvent`, `PlayerChangedDimensionEvent`. Persistence: `PlayerEvent.Clone` copies the capability when `!isWasDeath()` (dimension return from End) and when death with `keepInventory` (`world.getGameRules().getBoolean("keepInventory")`); on death without keepInventory, add belt stacks to `PlayerDropsEvent` drops (or drop in `LivingDeathEvent`) and clear - check no duplication. HUD: `RenderGameOverlayEvent.Post` with `ElementType.HOTBAR` (or ALL, once), `RenderHelper.enableGUIStandardItemLighting` + `mc.getRenderItem().renderItemAndEffectIntoGUI` + `renderItemOverlays`, positioned with `ScaledResolution`. Lang for key and category. In runClient: press R with sword/pick/empty hand, verify 4-step cycle and HUD, rebind in Controls, relog, go through Nether portal and back, die with keepInventory on and off, open LAN and check a second client's HUD only shows its own belt. Partly: cycling works in singleplayer but swap is done client-side (desyncs/ghost items after relog), or belt lost on dimension change, or HUD missing.

## S7 - Blast kiln multiblock

**Prompt:** I want a big Blast Kiln that you build out of blocks instead of crafting as one block. You craft Kiln Bricks and one Kiln Controller. The kiln is a 3x3x3 cube: 25 Kiln Bricks, the Controller in the middle of one side wall, and an empty hollow space in the very center. The Controller can face any side. When I right-click the Controller it either says "Kiln formed" or tells me what's wrong, like which position is missing a brick or that the middle isn't empty. Once formed, it smelts ores twice as efficiently as a furnace: one ore gives two ingots (anything a furnace would turn from an ore into an ingot, including other mods' ores). It needs coal or charcoal as fuel and takes about as long as a furnace per item. There's no screen; you use hoppers: hoppers pointing into any top-layer brick put ore in, hoppers into any brick on the middle ring add fuel, and hoppers pulling from any bottom-layer brick take the ingots out. If any block of the kiln is broken it stops working and the hoppers stop connecting until it's rebuilt, without losing what was inside. Breaking the Controller drops everything inside it. The ore multiplier and smelting time should be settings in the config. It would be nice if the bricks looked different when the kiln is formed and the center glowed while it's smelting.

**Grade:** Controller TE (`ITickable`) owning three `ItemStackHandler`s (input, fuel, output) persisted in NBT; validation scans the 3x3x3 relative to the controller (centre = `pos.offset(facing.getOpposite())`), returning the first offending `BlockPos` and reason for the chat message; re-validate on right-click, periodically (e.g. every 20 ticks) and/or when a brick's `breakBlock`/`neighborChanged` notifies controllers within range - formed state must also be re-checked after world load (do it lazily on first `update()`, not in `onLoad`/`readFromNBT`, since the world/neighbours aren't ready). Bricks proxy the item capability: bricks need a TE (or lookup) to find their controller and return `CapabilityItemHandler.ITEM_HANDLER_CAPABILITY` only when formed, with a wrapper that limits by layer (top = insert-only to input, accepting only stacks with a furnace result that are ore - `FurnaceRecipes.instance().getSmeltingResult(stack)` plus `OreDictionary.getOreIDs` names starting with "ore"; middle ring = insert-only fuel via `TileEntityFurnace.getItemBurnTime`/`isItemFuel`, optionally restricted to coal/charcoal; bottom = extract-only output). Unformed -> `hasCapability` false so hoppers stop (hoppers cache nothing, so this works). Smelting: burn-time/cook-time counters like a furnace, output `result.copy()` with count * multiplier, stop when output can't fit; changes `markDirty`. Config via `@Config` (multiplier int with `@RangeInt`, cook ticks), synced on `OnConfigChangedEvent`. Formed visuals: a FORMED blockstate property on bricks/controller (watch Forge's `TileEntity.shouldRefresh` default - modded TEs get recreated on state change unless overridden, losing inventory) and the centre glow via a light-emitting state, `getLightValue` on the controller, or a placed invisible light block - visuals are not required for full marks if formation/smelting are correct. Controller `breakBlock` drops handlers' contents (`InventoryHelper.spawnItemStack`) before `super.breakBlock`; breaking a brick keeps contents in the controller. Recipes for bricks and controller. In runClient: build the cube wrong (missing brick, block in centre, controller on a corner) and read messages; build right in all 4 orientations; hoppers with iron/gold ore on top, coal into the middle ring, hopper under a bottom brick into a chest; count ingots (2 per ore); break a brick mid-smelt (stops, hoppers stall, items kept), rebuild (resumes); save/reload mid-smelt; break controller (drops all); change multiplier in Mods > Config. Partly: forms and smelts but only through the controller block (no brick proxying), or formation not re-checked after reload/break, or inventory lost on state change.
