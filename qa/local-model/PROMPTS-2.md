# Local-model trial prompts, series 2 (S0-S7)

Held out: written without reading the kit's docs, tools or earlier results. Do not show this file to an agent or tune the kit to these prompts.
Paste only the **Prompt:** text, verbatim, into a fresh trial folder (S7b into the S7a folder). **Grade:** lines are for the human grader only.

## S0 - Copper ingot and block (smoke)

**Prompt:** I want copper in my game. Add a copper ingot item and a copper block. Nine ingots in the crafting table should make one block, and one block should turn back into nine ingots. Make them look orange-ish and have proper names in the game.

**Grade:** Works if both are registered with matching modid, the shaped 3x3 and shapeless 1-to-9 recipes exist as JSON under assets/<modid>/recipes, items and the block (with ItemBlock) have models and textures (no purple-black checkerboard), and lang entries show "Copper Ingot" / "Block of Copper" instead of raw keys. The block should need a pickaxe and drop itself. runClient: craft both ways, place and break the block, check names and textures in the inventory and in hand. Partly: a recipe missing or wrong direction, a raw lang key, or a missing texture on one of the two.

## S1 - Redstone grinder with progress bar

**Prompt:** I'd like a Grinder machine block. You put an ore in it (iron ore or gold ore) and after about 10 seconds you get 2 dust items out, which you can smelt into ingots in a normal furnace. It should only run while it has a redstone signal, and the window should have an arrow that fills up as it grinds, like the furnace. Hoppers should be able to put ore in from the top and take dust out from the bottom. If I break the machine it should drop whatever was inside, and it shouldn't lose its items if I quit and reload the world.

**Grade:** Needs a Block with a TileEntity (registered, ITickable) that only does work on the server (`!world.isRemote`), checks `world.isBlockPowered`/`isBlockIndirectlyGettingPowered` each tick, and stores input/output in an inventory (ItemStackHandler capability with sided access: top = input only, bottom = output extract only, or ISidedInventory) saved in write/readFromNBT along with progress. GUI via IGuiHandler + NetworkRegistry registration, a Container with slot transfer (shift-click must not dupe or crash) and a GuiContainer; progress must reach the client through Container `detectAndSendChanges`/`updateProgressBar` (or an equivalent packet), not by reading the server TE from the client. Two dust items with smelting recipes (GameRegistry.addSmelting) to iron/gold ingots; output stacking respects max stack size and stops when full; non-ore input rejected by the slot. On break, contents dropped (`breakBlock` + InventoryHelper) before the TE is removed. runClient: arrow animates only with a lever on, stops when the lever is off, hopper in/out works, reload keeps items and progress, breaking drops contents, a second player (or LAN) sees no desync. Partly: grinds but the arrow never moves (no sync), ignores redstone, hoppers unsupported, items lost on reload, or contents vanish on break.

## S2 - Ruined watchtower structure

**Prompt:** I want to find small ruined stone watchtowers while exploring. They should show up now and then in plains and forests, not too often, standing on the ground and not floating or buried. Make them look broken, like some blocks are missing and there's some mossy cobblestone. At the top there should be a chest with some random loot like bread, iron, arrows and sometimes a diamond.

**Grade:** Needs an IWorldGenerator registered with GameRegistry.registerWorldGenerator (or a decorate event handler), restricted to the overworld (dimension 0) and to plains/forest biomes (biome type or registry check), with a low chance per chunk. Placement must offset into the chunk (+8 on x/z) or otherwise stay within loaded chunks to avoid cascading worldgen (watch the log for "loaded a new chunk" warnings); ground found with getTopSolidOrLiquidBlock/getHeight and rejected on water or steep terrain. Randomized missing blocks and mossy cobblestone from the passed Random, not Math.random. Chest loot through a loot table JSON (assets/<modid>/loot_tables/...) registered with LootTableList and set via TileEntityChest.setLootTable, so loot is rolled on first open; hard-coded fixed items count as partly. Structure built with code or a .nbt template are both fine. runClient: new world, find one (creative flight or /locate is unavailable, so a debug log of placed coordinates is acceptable), check it sits on the ground, loot varies between chests, no generation in the nether, desert or ocean, no worldgen lag spam. Partly: generates everywhere or never, floats/buries, chest is empty or always identical, or cascading-worldgen warnings.

## S3 - Slingshot

**Prompt:** Add a slingshot I can make from sticks and string. It should work like a bow: hold right-click to pull it back and let go to shoot, and the longer you pull the farther and harder it shoots. Instead of arrows it shoots small pebbles, which I can craft from cobblestone, and it uses one pebble each shot unless I'm in creative. Pebbles should hurt mobs a bit and break when they hit something, and I want to actually see the pebble flying.

**Grade:** Item with `getMaxItemUseDuration` (72000), `getItemUseAction` BOW, `onItemRightClick` setting active hand only if ammo is present (or creative), and `onPlayerStoppedUsing` computing charge like ItemBow; ammo search through the inventory, consumed only when not creative. Projectile spawned server-side only (`!world.isRemote`) as an EntityThrowable (or EntityArrow subclass) registered with EntityRegistry.registerModEntity (unique id, tracking range, update frequency, velocity updates); impact deals DamageSource.causeThrownDamage with the shooter, then setDead. Rendering registered client-side in preInit via RenderingRegistry.registerEntityRenderingHandler with an IRenderFactory (e.g. RenderSnowball with the pebble item), in a client proxy, so a dedicated server does not crash. Durability on the slingshot is a plus; pull animation via item property overrides ("pull"/"pulling") is a plus, not required. Recipes for slingshot and pebbles. runClient: short tap vs full charge travel differently, ammo count drops in survival and not in creative, no fire without pebbles, the pebble is visible in flight (not invisible or a white cube), mobs take damage, no crash on hitting a block. Partly: fires instantly with no charge, invisible projectile, consumes ammo in creative, or client-only spawning (ghost projectiles that do nothing).

## S4 - Cauldron soaking recipes

**Prompt:** I want a new way to change items: if I right-click a cauldron filled with water while holding certain items, the item soaks and turns into something else, and the water level goes down by one. For example cobblestone turns into mossy cobblestone, stone bricks into mossy stone bricks, and coloured wool turns back into white wool. Each right-click should soak one item, not the whole stack. I'd also like to add my own soaking recipes in a config file without changing the code, and if I make a typo in the file it shouldn't crash the game.

**Grade:** Needs a recipe registry (input item + metadata or wildcard -> output stack) and a handler on PlayerInteractEvent.RightClickBlock (or similar) that checks the target is the vanilla cauldron with LEVEL > 0, runs only on the server, consumes exactly one input (not in creative is optional), gives the output (add to inventory or drop if full), lowers the level with BlockCauldron.setWaterLevel, and cancels the event so vanilla behaviour (filling bottles, washing leather) does not also fire for matched items, while unmatched items keep vanilla behaviour. Wool must match any colour (meta wildcard) and produce meta 0. Recipes loaded from a Forge Configuration string list (or a JSON file in config/) at init, default entries written when absent; malformed lines or unknown item ids logged as warnings and skipped, never a crash. Main-hand/off-hand double firing handled (no double soaking per click). runClient: each example works one item per click, level drops and stops at empty, a recipe added to the config works after restart, a deliberately broken line only logs a warning, filling a bottle from the cauldron still works. Partly: recipes hard-coded only, whole stack converted, level unchanged, wool colours not handled, client/server duplication, or a crash on a bad config line.

## S5 - Colour-linked shared chests

**Prompt:** My friends and I play on a server and want shared storage. Add a Linked Chest: if you right-click it with a dye, it takes that colour, and every linked chest of the same colour shares the same inventory, even if they're far apart or in the Nether. Only the person who placed a chest should be able to change its colour. If someone breaks a linked chest, the stuff inside shouldn't drop or disappear, because it belongs to the colour and is still there in the other chests.

**Grade:** Shared inventories stored per colour in WorldSavedData obtained from the global map storage (`world.getMapStorage()`, so it is the same in every dimension), with markDirty on every change and NBT read/write of all 16 inventories. TileEntity stores colour and owner UUID in NBT and syncs colour to the client (getUpdateTag/getUpdatePacket/onDataPacket + notifyBlockUpdate) so the tint/colour shows (via IBlockColor, a property, or TESR; any visible indicator is fine). Dye interaction server-side, owner check by UUID (not name), consumes one dye in survival, message to non-owners. GUI opens a Container backed by the shared inventory on the server so two players with the same colour open at once see each other's changes live and cannot duplicate items; the container must not cache a private copy. Breaking drops the chest block only. Must work on a dedicated server (no client classes in common code). runClient (ideally LAN with two clients, or two chests in two dimensions): same-colour chests share contents across dimensions, different colours do not, reload keeps contents, non-owner cannot recolour, breaking does not drop contents. Partly: sharing only within one dimension or per-chest storage, contents lost on reload, items dropped on break (duplication), recolour by anyone, colour not visible on clients, or desync/dupes with two viewers.

## S6 - Sparkling dyeable wizard hat

**Prompt:** I want a wizard hat you can wear on your head. It should be a tall pointy hat with a wide brim, sticking up above the player's head, not just a flat helmet texture. While you wear it, little sparkles should float around you every now and then. I'd like to dye it different colours in the crafting table like leather armor, and the colour should show both on my head and in my inventory.

**Grade:** ItemArmor in the HEAD slot with a custom armor material (low protection is fine), overriding `getArmorModel` (client-only, `@SideOnly(Side.CLIENT)`) to return a ModelBiped subclass with extra boxes on bipedHead forming brim and cone, copying the default model's pose/visibility; `getArmorTexture` points to a texture matching the model's UVs. Colour stored in NBT (display.color like leather or own tag); inventory tint via IItemColor registered in a client-side ColorHandlerEvent.Item/init; worn colour applied in the model render (GlStateManager.color) or a tinted texture layer. Dye recipe as a registered IRecipe (crafting with any dye, mixing like leather is a plus) that preserves the hat; washing in a cauldron optional. Sparkles spawned client-side only (world.isRemote in onArmorTick, random interval) with vanilla particle types; nothing client-only referenced from common code (dedicated server must not crash). runClient (all of this is visual): hat shape visible above the head in third person (F5) and not clipping badly, colour changes after dyeing both in inventory and on the head, sparkles appear while worn and stop when removed, other players see the hat. Partly: flat helmet texture only, dye recipe missing or colour only on one of icon/worn model, particles spammed every tick or spawned server-side, or a dedicated-server crash from client classes.

## S7a - Sapphire ore and tools (first part)

**Prompt:** Add sapphires to the game. Sapphire ore should be found underground, a bit more common than diamonds but in the same kind of depth, and mining it gives a sapphire gem (more with Fortune). With sapphires I want to craft a sapphire pickaxe and a sapphire sword that are a little better than iron but worse than diamond.

**Grade:** Ore block with harvest level 2 (iron pickaxe) and `getItemDropped`/`quantityDroppedWithBonus` for Fortune, silk touch returning the ore; generated with WorldGenMinable in the overworld at diamond-like heights (y up to ~16-20) through an IWorldGenerator with chunk offset, slightly more veins than diamond. Gem item, a ToolMaterial via EnumHelper.addToolMaterial between iron and diamond (harvest level 2 or 3, durability/speed/damage in between), ItemPickaxe (constructor is public; ItemAxe would not be) and ItemSword, repair item set to the gem, JSON recipes, models, textures, lang. runClient: find ore at low y, iron pickaxe mines it and stone does not, Fortune raises drops, tool stats in tooltips fall between iron and diamond. Partly: ore never generates or at all heights, drops the ore block always, tools with wrong stats or missing recipes.

## S7b - Sapphire armor with night vision (second part, same folder)

**Prompt:** Now add a full set of sapphire armor to the same mod, also between iron and diamond. When I'm wearing all four pieces and I'm deep underground, below about y 40, I should get night vision, and it should go away when I come back up or take a piece off. Don't break the ore and tools you already made.

**Grade:** Run in the S7a trial folder after S7a is finished, without resetting. Edits the existing mod (same modid, same registry names; no second mod class, no regenerated project that drops S7a content). ArmorMaterial via EnumHelper.addArmorMaterial with in-between durability/reduction, four ItemArmor pieces with armor textures (layer_1/layer_2 under textures/models/armor), recipes, models, lang. Full-set check server-side each tick (onArmorTick on one piece, or a PlayerTickEvent) with posY < 40; applies night vision with a short duration (> 200 ticks to avoid the flicker warning near expiry) refreshed while valid, and removes it (or lets it lapse quickly) when conditions fail, without removing night vision from a potion the player drank (a plus, not required). runClient: S7a still works (ore generates, tools craft), armor renders on the player, night vision turns on below y 40 with all four pieces and off above it or with one piece removed, no flicker. Partly: armor works but S7a content broke or was duplicated, effect never removed, effect applied with fewer than four pieces, armor invisible when worn, or effect only on the client.
