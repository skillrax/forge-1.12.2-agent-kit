## State the budget before coding

Defaults: generator 1,000 RF/t (2,000 upgraded); cable 60,000 RF/t; storage 2,000,000 RF with 60,000 input and 20,000 output per tick; sink request 0–100,000 RF/t, default 1,000. Storage faces are world directions, OFF/IN/OUT; EAST defaults OUT, the rest IN. Side views read current permissions on each call, so a held capability does not retain an old face setting. Unsided storage access is closed. Fuel automation sees only the solid slot; the upgrade is GUI-only for both Forge handlers and vanilla hoppers.

Each cable spends one unit per RF delivered along its selected path, including ingress. All faces, sources, consumers and both directions share that cable's gross-flow allowance. A shared segment cannot exceed its rate; disjoint paths can exceed that rate across the whole component. Direct machine adjacency uses endpoint budgets. Storage output is one combined allowance for active pushing **and external extraction**; reception and sink demand also share allowances across faces. A face wrapper, simulation, graph rebuild, split/merge or same-tick cable replacement must not create a new allowance. The world/position ledger resets only when the world tick changes; it holds no energy.

Generation and storage push at server world-tick END. Source/face ordering rotates; traversal uses available paths, without equal-allocation or performance guarantees. Multiple storage devices can redistribute energy if their IN/OUT faces connect into the same component; define faces to express the intended topology. A source excludes itself from its route.

## Exact fuel economy and backpressure

Solid fuels use the current furnace burn-time registry, excluding lava buckets. A fuel item prepays `burn ticks × base RF/t × base fuel cost` ledger units. Solid takes priority over lava when a new reserve is needed. Lava initially supplies 1,000 base RF/mB in an 8,000 mB tank, filled by right-clicked buckets or fluid capabilities. Other fluids are rejected. Containers left by a burned item are retained or dropped when the remaining stack occupies the fuel slot.

The upgrade doubles output while using 1.5× fuel per full running tick: it costs **0.75× fuel per RF**, not 1.5× per RF. Defaults use four integer units/base RF and three/upgraded RF. One mB supplies 4,000 units; upgraded 1 mB yields 1,333 RF and retains one unit. Debit whole items/mB before delivery and retain exact fractional credit. Do not round every request, use floating-point accumulation, discard leftovers, or refund consumed items on a settings change. Changing an upgrade applies its current cost to the existing reserve. Simulation changes nothing; absent/full/zero-demand destinations spend no fuel. Credit, inventory, tank, RF and controls are saved in NBT.

`NetworkSettings` is source-time tuning, not a runtime config loader. Keep rates/capacities/costs positive, sink demand nonnegative and display/action ranges bounded. Preserve integer units across saves: changing their meaning or changing fuel values under an existing world needs an explicit migration policy. The current generator simulation values one pending solid item plus saved credit/lava; a single call does not assume the entire stack has already burned. Retain that policy or deliberately add bounded multi-item consumption for much larger rates. Rate/recipe/cosmetic variants do not require another proof campaign.

## Bufferless transactions

Cable stored/max RF are both zero. Simulation builds virtual reservations for **both paths and endpoints**, subtracting repeated assignments to the same tile through different faces. Otherwise a loop or shared receiver can appear to accept the same allowance repeatedly. Commit reacquires the receiver and checks every cable still belongs to the loaded route. Actual acceptance, not the simulated number, determines cable expenditure.

Native sources extract before delivering. If a receiver accepts less at commit, restore the undelivered RF or exact fuel credit at the source. Keep the attempted source allowance spent for that tick; cable allowance counts only actual delivery. An externally pushing source receives the cable's actual accepted count and retains the rest according to the FE contract. No energy lives in the graph, so cable removal cannot destroy buffered RF. Ordinary breaking of generator/storage discards that machine's energy/fluid/credit/settings and drops its inventory; add state-preserving pickup only when requested.

Handlers returning negative/excessive committed counts are rejected. Arbitrary reentrant or noncompliant handlers are not proven safe. These transactions establish native accounting, not universal compatibility.

## Loaded means server resident, not visible

In pinned 1.12.2, `World.getTileEntity` reaches `ChunkProviderServer.getLoadedChunk`, which clears `unloadQueued`. An `isBlockLoaded` guard prevents loading an already-absent chunk but can still cancel pending unloading. `LoadedView` builds a short-lived index from `getLoadedChunks()`, rejects queued or absent chunks, and reads existing tile maps without loading/creating tiles. It is rebuilt per synchronous operation rather than caching neighbors across ticks. Server cable-shape queries use the same safe path. See [shared chunk safety](machines-and-energy.md#chunk-safety-and-dirty-marking) for dirty notifications and inventories.

Test the pending-unload timing once: queue an intermediate cable chunk after provider ticking but before network END, then observe its flag and actual absence through existing collections. QA calls to `getLoadedChunk` can themselves clear the flag. During absence, energy and fuel must remain unchanged; deliberate reload must resume conservation. Reacquire restored tiles instead of examining obsolete objects. The promoted starter also rejects held FE ports of queued/replaced tiles, uses safe owner-chunk dirty marking, and checks menu access without a loading tile lookup. This closes neighboring adaptation paths beyond the original routing fix; focused starter checks verify them.

Spawn chunks remain resident around world spawn, and player-loaded chunks can complete a long route. In this pinned version the spawn rule uses chunk centers within ±128 blocks of spawn in X/Z; player radius has a minimum of three. Single-player render distance affects server view distance; dedicated-server view distance is separate. F3+A reloads client renderers, not server chunks. Fast flying and visible terrain are not evidence of actual unloading. The accepted replay showed a far route stopping while a near-spawn route remained fully resident and transferred normally. No chunkloader is included.

## Controls, interoperability and checks

Large RF/settings values use two unsigned 16-bit halves reconstructed from signed-short window properties. Keep field counts, server sends, client application and NBT aligned. The sink display snapshots the last completed tick, so syncing before routing does not falsely show zero. Vanilla `CPacketEnchantItem` action IDs are bytes; use the bounded custom packet for numeric demand. The server schedules it on its main thread and validates the open container, window ID, distance and action range. Preserve typed input while editing; apply the saved default after initial property synchronization. Client rendering stays behind the client proxy/subscriber.

The actual energy API is Forge `CapabilityEnergy.ENERGY` / `net.minecraftforge.energy.IEnergyStorage`, using the neighbor's opposite face; RF is the display unit. Legacy `cofh.redstoneflux.api.IEnergyReceiver` is a distinct sided interface, not automatically implemented by an FE capability. Primary reference: [CoFH's 1.12 API](https://github.com/CoFH/RedstoneFlux-1.12-Legacy/blob/1.12/src/main/java/cofh/redstoneflux/api/IEnergyReceiver.java). No third-party classes/dependencies are bundled. Native FE and a QA-only partial-acceptance handler were tested; Ender IO, Thermal and CoFH integration were not. Cables accept active pushes but expose no extraction; pull-only consumers can extract from an OUT storage face. The generator actively pushes and reports zero stored RF for its generated-on-demand port.

For changed routing/fuel logic, use a short exact accounting scenario plus the affected backpressure/topology boundary. Saved-state changes need a save/reload observation; controls/layout changes need a real client check. Build/server readiness alone is not behavior evidence. The basis has accepted single-player manual operation/save-restart, exact fuel/shared-budget/branch-loop checks, a reproduced/fixed pending-unload defect and normal player-residency replays. Installed hashes and multiplayer/modpack coverage are limited. The promoted starter gets extraction/build and focused adaptation checks; do not demand another full user campaign for names/tuning. Keep QA outside production resources/JARs. Traversal rebuilds topology per offer for simplicity; profile an actual workload before making large-network or performance-parity claims.
